# Промпт: свой дашборд аналитики Claude Code

Скопируй этот файл целиком в первое сообщение новой сессии Claude Code, открытой в этой директории.

## Контекст и мотивация

Мы пробовали `npx claude-code-templates@latest --analytics` (aitmpl.com, репозиторий
davila7/claude-code-templates, версия на момент теста v1.29.4). Обнаружили реальные баги,
подтверждённые вручную (curl + браузерные devtools):

1. Кнопки диапазона `7D / 30D / 90D / All` в UI переключаются визуально, но НЕ дают эффекта:
   при клике не уходит ни одного нового сетевого запроса, а backend-эндпоинт `/api/data`
   полностью игнорирует query-параметры диапазона (`?range=`, `?days=` и т.п.) — всегда
   отдаёт один и тот же полный набор данных.
2. UI жёстко завязан на WebSocket (`ws://localhost:3334`) для первого рендера — если сокет
   не установился, все виджеты вечно висят на skeleton-заглушках со статусом "Connecting…",
   даже когда REST API уже отвечает валидными данными. Помогает только ручной клик по Refresh.
3. Встроенный file-watcher реагирует на дозапись `.jsonl`-файла ТЕКУЩЕЙ сессии Claude Code
   (в которой открыт сам дашборд) и на каждое новое сообщение запускает полный пересчёт
   всех файлов истории (у нас — 417 файлов). Это создаёт петлю обратной связи: чем активнее
   работаешь в Claude Code, тем чаще пересчитываются ВСЕ разговоры, что раздувает память
   процесса (Node RSS уходил за 1.2 ГБ, сервер уходил в `status: "warning"` по
   `memory_threshold`, WebSocket-соединения рвались с кодом 1006).

Вывод: хотим свою версию — проще, без live-polling/WebSocket-магии, с рабочей фильтрацией
по датам и без петли пересчёта.

## Цель

Локальный дашборд аналитики использования Claude Code: сколько токенов потрачено, сколько
разговоров/сессий, по каким проектам, какие агенты/навыки вызывались чаще всего, активность
по дням — с РАБОЧИМ фильтром по периоду (7 дней / 30 дней / 90 дней / всё время).

## Стек

- **Nuxt 4** (последняя стабильная), TypeScript.
- Nitro server routes (`server/api/*.ts`) для чтения и агрегации данных — без отдельного
  Express/Fastify бэкенда, всё в рамках Nuxt.
- Vue 3 Composition API для фронта.
- Графики: любая лёгкая библиотека с хорошей поддержкой Vue/SSR (например `unovis`,
  `vue-chartjs`/Chart.js, или ECharts через `vue-echarts`) — выбери сам, обоснуй выбор
  в 1-2 предложениях перед началом кодинга.
- Без Pinia, если состояние тривиальное — обычные composables/`useFetch` вполне достаточно.

## Источник данных — формат, ПРОВЕРЕННЫЙ вручную

Claude Code пишет историю в:

```
~/.claude/projects/<project-slug>/<session-uuid>.jsonl
```

где `<project-slug>` — это путь рабочей директории с заменой `/`, `\`, `:`, пробелов на `-`
(например `C:\Users\Al\Desktop\education\Vibe\agents` → `C--Users-Al-Desktop-education-Vibe-agents`).

Каждый файл — построчный JSON (одна запись = одна строка). Реально встреченные типы записей
(`type`):

- `"mode"` — служебная, в начале файла.
- `"file-history-snapshot"` — служебная, снапшоты файлов.
- `"user"` — сообщение пользователя. Поля: `message.role`, `message.content` (строка либо
  массив блоков), `timestamp` (ISO8601), `cwd`, `sessionId`, `gitBranch`, `version`,
  иногда `isMeta: true` для служебных/системных вставок (например local-command-caveat) —
  их обычно стоит исключать из "реальных" сообщений пользователя.
- `"assistant"` — ответ модели. Ключевое поле — `message.usage`:
  ```json
  {
    "input_tokens": 2,
    "output_tokens": 322,
    "cache_creation_input_tokens": 19324,
    "cache_read_input_tokens": 42756,
    "output_tokens_details": {"thinking_tokens": 217},
    "service_tier": "standard"
  }
  ```
  Также есть `message.model` (например `"claude-sonnet-5"`) и `message.content` — массив
  блоков с `type`: `"thinking"`, `"text"`, `"tool_use"` (есть `id`, `name`, `input`),
  бывают и другие. Для подсчёта токенов суммируй `input_tokens + output_tokens +
  cache_creation_input_tokens + cache_read_input_tokens` по всем `assistant`-записям
  (реши сам, включать ли кэш-токены в "общие токены" или показывать их отдельной
  категорией в stacked-графике "Input / Output / Cache" — так сделано у аналога).

- Вызовы инструментов/агентов — ищи блоки `content[].type === "tool_use"` с
  `name === "Agent"` (или `"Task"` в других версиях Claude Code) — в `input` там обычно
  лежит что-то вроде `subagent_type`/`description`. **Перед тем как на это полагаться —
  найди в реальных файлах пользователя хотя бы один такой блок и провалидируй точные
  названия полей** (`python -c "..."` по `~/.claude/projects/**/*.jsonl` — не хардкодь
  вслепую).

Верхнеуровневые поля записи (не внутри `message`): `sessionId`, `cwd`, `timestamp`, `uuid`,
`parentUuid`, `gitBranch`, `version`.

## Обязательные метрики (минимум — как в дашборде аналога, но РАБОЧИЕ)

1. **Total tokens** — сумма токенов за выбранный период (см. фильтр ниже).
2. **Conversations** — число файлов `.jsonl` (= разговоров) с активностью в периоде.
3. **Sessions / Active** — сколько разговоров имели сообщения в последние N дней.
4. **Agent uses** — количество вызовов sub-agents, сгруппированное по имени/типу.
5. **Token Usage Over Time** — stacked-график (input / output / cache) по дням за период.
6. **Activity Heatmap** — календарная теплокарта (день → кол-во сообщений/токенов),
   в духе GitHub contributions graph.
7. **Agent Usage** — горизонтальный bar-chart, топ агентов по количеству вызовов.
8. **Projects** — bar-chart, топ проектов (`project-slug`) по количеству разговоров.
9. **Token Distribution** — разбивка input/output/cache суммарно за период.
10. **Recent Conversations** — список последних N разговоров с датой, кол-вом сообщений,
    токенов, проектом.

## Обязательное требование — фильтр по периоду ДОЛЖЕН реально работать

Это главная причина, почему мы это затеяли. Конкретно:

- Фильтр (`7D / 30D / 90D / All`) должен быть либо query-параметром реального
  server API endpoint (`/api/analytics?range=30d`), который на бэкенде фильтрует
  сообщения по `timestamp` ПЕРЕД агрегацией, либо — если решишь агрегировать всё на
  клиенте — должен реально пересчитывать все виджеты при смене значения (проверь это
  руками в браузере: цифры должны меняться при переключении диапазона).
- Добавь простой Playwright/Vitest smoke-тест (или хотя бы ручную проверку с
  скриншотами до/после), который фиксирует, что смена диапазона меняет хотя бы
  "Total tokens".

## Производительность — не повторяй чужих ошибок

- НЕ делай file-watcher, который на любое изменение любого `.jsonl` (включая тот, в
  котором сейчас пишется текущая сессия дашборда) пересчитывает ВСЁ. Если делаешь
  live-обновление — инкрементально пересчитывай только изменившийся файл (сравнивай
  `mtime`+`size`, кэшируй распарсенный результат на файл).
- Никакого обязательного WebSocket для первого рендера. Первая загрузка — обычный
  `GET`, страница должна показывать данные без танцев с сокетом. WebSocket (если
  вообще нужен) — только опциональный push поверх уже отрендеренных данных.
- Кэшируй агрегаты (in-memory, ключ — диапазон + hash списка файлов/mtime), не
  перечитывай 400+ файлов на каждый чих.
- Путь к данным — бери из `~/.claude/projects` кроссплатформенно
  (`os.homedir()` / `process.env.USERPROFILE` на Windows), не хардкодь `C:\Users\Al`.

- Тёмная тема по умолчанию (как у аналога), можно светлую как опцию.
- Русский или английский интерфейс — на усмотрение (данные и так локальные, аудитория —

## Упаковка в CLI-пакет (`npx <пакет> --analytics`)

Хотим тот же UX, что у оригинала: одна команда в терминале — установка + запуск.
Реализация:

1. Собрать Nuxt в standalone-сервер: `nuxt build` → `.output/server/index.mjs`
   (Nitro preset `node-server`, он же дефолтный).
2. Добавить тонкий CLI-скрипт `bin/cli.mjs`, который:
   - парсит флаг `--analytics` (и, по желанию, `--port`);
   - поднимает `.output/server/index.mjs` (или импортирует и стартует его programmatically);
   - открывает браузер на `http://localhost:<port>` (`open`/`opener`-пакет либо
     `child_process.exec('start ...')` кроссплатформенно через пакет `open`).
3. В `package.json` прописать `"bin": { "<имя-команды>": "./bin/cli.mjs" }` и `"files"`
   со списком того, что реально нужно в паблише (`.output`, `bin`, README, package.json) —
   НЕ публикуй `.nuxt`, `node_modules`, исходники `server/`/`pages/` без надобности.
4. Локально без публикации: `npm install -g .` из корня проекта — дальше команда
   доступна глобально без npx. Это самый простой путь для личного использования, без
   публикации в реестр.

## Чек-лист публикации в npm (если решим публиковать по-настоящему)

- [ ] Аккаунт на npmjs.com, `npm login` в терминале.
- [ ] Имя пакета: если хочешь короткое имя без скоупа — проверь, что оно свободно
      (`npm view <имя>`, 404 значит свободно). Проще и безопаснее — скоупнутое имя
      `@ник/имя` (скоупы почти всегда свободны), но тогда паблишить нужно с флагом
      `--access public`, иначе npm по умолчанию считает скоуп-пакет приватным/платным.
- [ ] `package.json`: `name`, `version` (начни с `0.1.0`), `description`, `license`,
      `bin`, `files`, `engines.node` (минимальная версия Node), `repository` (если есть
      публичный git-репозиторий).
- [ ] **Проверить, что в бандл не попадают персональные данные/пути конкретно этой
      машины** — путь к `~/.claude/projects` должен резолвиться в рантайме
      (`os.homedir()`), не быть захардкожен на этапе сборки; в `.output` не должно
      случайно оказаться сохранённых данных из тестовых запусков.
- [ ] `.npmignore` или `"files"` в package.json — исключить исходники, тесты,
      `.env`, скриншоты, всё лишнее.
- [ ] Локальный дымовой тест перед паблишем: `npm pack` → `npm install -g
      ./<имя>-<версия>.tgz` → запустить команду в чистом терминале → убедиться, что
      дашборд поднимается и фильтр по датам работает.
- [ ] `npm publish` (с `--access public` для скоупа).
- [ ] Проверить, что `npx <имя-пакета>@latest --analytics` реально работает "с нуля"
      (лучше всего — на другой машине или хотя бы после `npm cache clean`).
- [ ] Дальнейшие релизы: `npm version patch|minor|major` → `npm publish`. Помни, что
      удалённое из npm имя пакета какое-то время нельзя переиспользовать — выбирай имя
      осознанно с первого раза.

## Что делать в начале новой сессии

1. Прочитай этот файл целиком.
2. Сам исследуй 2-3 реальных `.jsonl`-файла из `~/.claude/projects/**` (через Python/Node
   скрипт, не через угадывание) — подтверди или скорректируй схему данных выше, особенно
   часть про `tool_use`/agent-вызовы.
3. Предложи короткий план (архитектура + порядок реализации), прежде чем писать код.
4. Реализуй `server/api` роуты агрегации, потом фронт.
5. Проверь фильтр по датам руками в браузере (Claude in Chrome tools) — обязательно
   зафиксируй, что смена диапазона реально меняет цифры, прежде чем считать задачу
   готовой.
